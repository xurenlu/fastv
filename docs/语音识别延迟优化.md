# 语音识别延迟优化（2.5.0-rc6）

> 对应版本：v2.5.0-rc6 ｜ 测量机器：MacBook（Apple M2，4 性能核 + 4 能效核，24GB）

## 问题

用户反馈：说完一句停顿下来，或者松开快捷键之后，经常还要再等好几秒才出字。

从本机 `voiceInputHistoryRecords` 里 95 条带耗时的真实记录看：

| 指标 | 数值 |
| --- | --- |
| 识别耗时 / 语音时长，中位数 | 0.25 |
| 识别耗时 / 语音时长，p90 | 1.57 |
| 最慢一次 | 25 秒 |

中位数不算差，但 p90 是中位数的 6 倍，而且 1~2 秒的短句经常要 6~8 秒。**波动本身就是体验问题**：用户无法预期要等多久。

## 根因

不是模型不行，是四处配置和流程各拖一段，叠加起来才有那几秒。

### 1. ONNX 线程配置踩了两个坑

```swift
// 旧：max(4, 逻辑核数) —— 在 M2 上等于 8
let numThreads = max(4, ProcessInfo.processInfo.activeProcessorCount)
```

Apple Silicon 的逻辑核数包含能效核。把 8 个线程铺开，整个并行区被最慢的能效核拖住。同时 ONNX Runtime 的线程池默认**自旋等待**：空闲工作线程忙等下一个并行区，机器一忙就和别的进程互相抢核。

交错基准（同一进程内每轮把所有配置各跑一次，让背景负载公平地落在每个配置上，负载约 13）：

| 配置 | 2 秒语音 | 6 秒语音 | 首次推理 |
| --- | --- | --- | --- |
| 8 线程 + 自旋（旧） | 219ms | 479ms | 517ms |
| 8 线程，关自旋 | 74ms | 156ms | 163ms |
| 4 线程 + 自旋 | 62ms | 152ms | 323ms |
| **4 线程，关自旋（新）** | **69ms** | **151ms** | **203ms** |
| 3 线程，关自旋 | 73ms | 161ms | 234ms |

两个坑各自都足以造成问题，合在一起最差。新配置取「性能核数（上限 8）+ 关自旋」：稳态与最快配置持平，首次推理更好，而且空闲时不再空烧 CPU 和电量——对一个常驻后台的菜单栏工具，这一条本身就值。

### 2. 模型 5 分钟空闲就被卸载

```swift
private static let inactivityThreshold: TimeInterval = 300  // 旧
```

而 fp32 模型重新加载要 12~19 秒。用户「隔一会儿再说一句」必然撞上冷加载——历史记录里 1~2 秒短句耗时 6~8 秒的，基本都是这么来的。

现在按变体决定：加速版常驻内存约 250MB，不再定时卸载；历史 fp32 接近 1GB，保留 30 分钟空闲阈值。两者在进程内存超过 4GB 时都会被卸。

### 3. 启动预热的 QoS 把整个进程钉死

ONNX Runtime 的线程池在**建会话时懒创建**，这些线程继承创建者的 QoS 并一直沿用。`2.0.0-rc10` 为了不让模型加载拖慢启动首屏，把预热降到了 `.utility`——副作用是此后进程内**每一次**推理都跑在低优先级线程池上，实测慢 1.5~2 倍。

现改回 `.userInitiated`。启动首屏的诉求由调用方的延迟满足（主窗口 1.5 秒、静默启动 3 秒之后才预热）。**日后若又出现「启动变慢」，请加大调用方延迟，不要把优先级降回 `.utility`。**

### 4. 加载后第一次推理额外慢

惰性分配（内存 arena、线程池、算子 kernel）都在第一次 `Run` 时做掉：本机 203ms，稳态 69ms。这 130ms 原本全记在用户第一次说话上。现在加载完立刻用一段静音空跑一次预热。

### 5. 松键后的两段等待被串起来算

```swift
// 旧：先睡满尾缓冲，再去等上一段转写
try? await Task.sleep(...)          // 尾缓冲 0.3s
await incrementalTranscriptionTask?.value   // 等 CPU 算完上一段
```

两件事互不依赖：前者在等麦克风多收 0.3 秒，后者在等 CPU。串行做等于时间相加。现改为 `async let` 并发，只花两者中较长的那个。

### 6. 智能分段模式白白重采样整段录音

该模式的最终文本来自各分段加末段，整段 PCM **从来没被用过**，但 `stopRecording()` 照样把它拼接 + 重采样一遍——说得越久这一步越贵。现在该模式走 `stopRecordingDiscardingAudio()`，只停引擎不转码。

顺带修掉 `buffers.reduce(Data(), +)`：每加一段都新分配一块并整体拷贝，复杂度是段数的平方。改为预留容量后逐段 append。

## 换模型：官方 int8 量化版

从 `iic/SenseVoiceSmall-onnx` 取官方 `model_quant.onnx`（241,216,270 字节），托管到 `img.niuwoai.com/models/sensevoice-small/model.int8.onnx`。

准确率验证分两层，缺一不可：

1. **离线对照**：15 句中文 TTS 素材上，官方 int8 与 fp32 输出**逐字完全一致**（0.00% 差异）。
2. **App 自己的管线**：走 kaldi-native-fbank → LFR → CMVN → ONNX → CTC 解码的完整链路跑同一批素材，字错率 3.36%（错的是「11点半 vs 十一点半」这类数字规范化和英文术语，与 fp32 同款）。这一层必须做——离线用 Python 复现的特征提取证明不了 App 的 fbank 实现在量化模型上同样稳。

模型体积同时从 894MB 降到 230MB，新用户首次下载快很多。

## 结果

### 端到端（Release 构建，App 自己的完整链路，机器空闲）

15 句素材，语音时长 5.0~6.8 秒：

| 指标 | 数值 |
| --- | --- |
| 识别耗时中位数 | 0.130s |
| 最慢 | 0.172s |
| 实时率（识别耗时 / 语音时长） | 0.02 |
| 字错率 | 3.36% |

也就是说，音频到手之后 0.13 秒出字。加上 0.3 秒尾缓冲，用户松开快捷键到文字上屏在半秒以内。

### 新旧配置同条件交错对比

| 配置 | 2 秒语音 | 6 秒语音 | 12 秒语音 |
| --- | --- | --- | --- |
| 改造前 fp32 / 8 线程 / 自旋 | 1714ms | 4460ms | 7587ms |
| 改造后 int8 / 4 线程 / 不自旋 | 185ms | 459ms | 1139ms |
| 提速 | 9.2x | 9.7x | 6.7x |

机器很空闲时差距会收窄到 3 倍左右（6 秒语音 479ms → 151ms）。**负载越高差距越大**，正好对上用户「有时候快、有时候要等好几秒」的体感——旧配置在机器忙时会雪崩，新配置不会。

## 双变体共存与升级

加速版落 `model.int8.onnx`，历史版本落 `model.onnx`，加载时优先加速版。老用户升级 App 后：

- 不重新下载也能立刻拿到线程、常驻、预热三项提速；
- 设置页「模型文件状态」出现升级入口，装好加速版后询问是否删除旧的标准版以释放约 894MB；
- 模型下载地址默认指向官方加速版，历史默认地址做一次性迁移，用户手填过的自定义地址不动。

## 怎么复测

单元测试（默认跳过端到端那条）：

```bash
bash scripts/run_unit_tests.sh
```

端到端识别验证，需要本机已装模型，并准备一个装着 16kHz 单声道 wav 与同名 `.txt` 参考文本的目录：

```bash
TEST_RUNNER_QECHO_ASR_FIXTURE_DIR=/path/to/fixtures bash scripts/run_unit_tests.sh
```

注意两点：`xcodebuild` 不会把 shell 环境透传给测试进程，必须加 `TEST_RUNNER_` 前缀；Debug 构建下 Swift 标量循环（CTC 解码那类）比 Release 慢一个数量级，量绝对耗时要用 Release。另外测试是多套件并行跑的，量性能时用 `-only-testing:` 单独跑，并留意 `sysctl -n vm.loadavg`——机器忙的时候任何绝对数字都不可信。
