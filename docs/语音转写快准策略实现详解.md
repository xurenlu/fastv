## 一、问题背景：速度与准确率的矛盾

在语音转文字（ASR）场景中，存在一个经典矛盾：

- **追求速度**：用户一停顿就立刻转写，反馈快、体验好，但短片段（如 1～2 秒）的识别准确率往往较低
- **追求准确**：等用户说完再整段转写，长音频上下文更完整，准确率更高，但用户需要等更久

尤其在「按住说话」的交互模式下：

- 用户可能连续说几十秒甚至几分钟
- 若只在松键时一次性转写，等待时间长
- 若按停顿频繁切小段转写，又容易产生碎片化、错误率上升

因此需要一套策略，在**不牺牲响应速度**的前提下，**尽量提升最终转写准确率**。

---

## 二、核心思路：双路径并行

我们采用「**快路径 + 准路径**」双路径并行：

| 路径 | 目标 | 触发时机 | 输出 |
|------|------|----------|------|
| **快路径** | 尽快反馈 | 检测到停顿（如 0.8 秒） | 单段转写结果，先缓存 |
| **准路径** | 提升准确率 | 累积到多段后 | 多段音频拼接后整段转写 |

两条路径同时进行，互不阻塞。松键时：

- 若准路径已完成 → 用准路径结果**替换**对应零碎结果
- 若未完成 → 仍使用快路径的零碎结果，保证不卡顿

这样既保证「边说边转」的即时感，又能在条件满足时用更准确的结果替换。

## 三、整体架构

### 3.1 数据流概览

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         用户按住快捷键说话                                  │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  静音检测器 (SilenceDetector)                                             │
│  - 阈值：默认 0.8 秒停顿                                                    │
│  - 混合检测：绝对阈值 + 相对下降（说话后突然安静）                            │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                    检测到有效静音段 │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  【快路径】提取当前段落 → 立即转写 → 缓存（音频 + 文本）                       │
│  - 单段转写，响应快                                                        │
│  - 每段至少 1 秒，过短则跳过                                                │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                    累积 ≥ 3 段     │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  【准路径】动态规划分批 → 多段音频拼接 → 二次转写                             │
│  - 每批至少 3 段、至少 3 秒                                                 │
│  - 多批可并行转写                                                          │
└─────────────────────────────────────────────────────────────────────────┘
                                    │
                    用户松开快捷键   │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  合并输出                                                                  │
│  - 对每批：有准路径结果则用准路径，否则用快路径零碎结果                         │
│  - 加上「剩余段落」（最后一次停顿到松键之间的内容）                            │
│  - 纠错 → 可选 AI 优化 → 插入到当前输入框                                    │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.2 关键数据结构

```swift
/// 单段结果：同时保存音频和转写文本（音频用于二次拼接）
struct IncrementalSegmentInfo {
    let audio: VoiceRecording   // PCM 数据，16kHz 单声道
    let transcript: String      // 快路径转写结果
}

// 快路径缓存：按时间顺序的段落列表
var incrementalTranscriptionResults: [IncrementalSegmentInfo]

// 准路径：动态规划后的分批方案及每批的转写结果
var incrementalBatchPartition: [Range<Int>]   // 如 [0..<4, 4..<7]
var incrementalBatchRefinedTexts: [String?]   // 每批的二次转写结果，nil 表示未完成
```

## 四、快路径：尽早转写

### 4.1 静音检测

- **停顿阈值**：默认 0.8 秒（可配置），检测到即触发段落切分
- **检测方式**：
  - 绝对阈值：RMS 低于某值视为静音
  - 相对下降：说话后电平明显下降（如降到峰值的 25%）也视为停顿
- **单段最小时长**：约 1 秒，过短段落不单独转写，避免无意义短片段

### 4.2 段落提取与转写

- 从 `VoiceInputService` 提取当前段落的 PCM 数据
- 调用 `SpeechTranscriber` 进行转写（本地 ASR 模型）
- 可选：自动纠错（常见错误、同音字等）
- 将结果存入 `IncrementalSegmentInfo`，同时保留音频供准路径使用

### 4.3 串行保证

- 段落转写是串行的：每次只处理一个段落，保证顺序
- 用户可继续说话，下一段会排队等待

## 五、准路径：动态规划分批

### 5.1 为何要「至少 3 段」

- 仅 2 段拼接，效果提升有限
- 3 段及以上，上下文更完整，准确率提升更明显
- 因此我们设定：**至少 3 段才触发准路径**

### 5.2 为何要「至少 3 秒」

- 过短音频（如 1～2 秒）对 ASR 不友好，易出现识别不稳
- 每批至少 3 秒，避免产生新的「短片段」问题

### 5.3 动态规划分批算法

目标：在满足「每批 ≥ 3 段、≥ 3 秒」的前提下，**尽量让每批更长**，以提高准确率。

**伪代码：**

```
函数 partition(segments):
    若 总段数 < 3: 返回 []
    结果 = []
    start = 0
    当 start < 总段数:
        剩余 = 总段数 - start
        若 剩余 < 3:
            合并到上一批（或单独成批）
            退出
        bestEnd = start + 3
        累计时长 = 前 3 段时长之和
        // 若不足 3 秒，继续加段
        当 累计时长 < 3.0 且 bestEnd < 总段数:
            bestEnd += 1
            累计时长 += 第 bestEnd 段时长
        // 若剩余不足 3 段，全部并入当前批
        若 总段数 - bestEnd 在 (0, 3) 之间:
            bestEnd = 总段数
        否则:
            // 尽量扩展当前批，在保证剩余可成批的前提下
            对 end 从 bestEnd+1 到 总段数:
                若 累计时长 >= 3 且 (剩余=0 或 剩余>=3):
                    bestEnd = end
        结果.append(start..<bestEnd)
        start = bestEnd
    返回 结果
```

**示例：**

| 总段数 | 分批方案 | 说明 |
|--------|----------|------|
| 3 段 | [3] | 一整批 |
| 6 段 | [6] 或 [3,3] | 若每段约 1 秒，可能 [6]；若每段很短，可能 [3,3] |
| 7 段 | [3,4] 或 [4,3] 或 [7] | 尽量让首批更长 |
| 9 段 | [6,3] 或 [9] | 优先整批或 6+3 |

### 5.4 批次并行转写

- 每次新增段落时，按当前段数**重新规划**分批
- 取消旧任务，按新方案启动新任务
- 每批单独一个 `Task`，多批并行执行
- 每批内部：拼接 PCM → 调用转写 → 写回结果

```swift
// 7 段 → 4+3 两批，并行转写
for (index, range) in partition.enumerated() {
    let task = Task {
        let refined = await runBatchRefinementTranscription(segments: segments[range], ...)
        incrementalBatchRefinedTexts[index] = refined
    }
    incrementalBatchRefinementTasks.append(task)
}
```

## 六、松键时的合并逻辑

### 6.1 按批合并

对每一批：

- 若 `incrementalBatchRefinedTexts[i]` 非空 → 使用准路径结果
- 否则 → 使用该批内各段的快路径转写结果拼接

最终文本 = 各批结果按顺序拼接。

### 6.2 剩余段落

- 从「最后一次停顿」到「松键」之间的内容，单独作为「剩余段落」
- 剩余段落单独转写后，拼接到最终文本末尾

### 6.3 不等待准路径

- 松键时**不**等待未完成的准路径任务
- 已完成则用准路径，未完成则用快路径，保证不卡顿

         │         │         │         │         │         │         │         │

         │         │         │         │         │         │         │         │

## 八、配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `silenceDetectionDuration` | 0.8 秒 | 停顿多久触发段落切分 |
| `incrementalBatchMinSegments` | 3 | 至少几段才触发准路径 |
| `incrementalBatchMinDuration` | 3.0 秒 | 每批至少多少秒 |
| `voiceInputReleaseTailBufferSeconds` | 0.3 秒 | 松键后继续录多少秒，减少尾部丢失 |

## 九、实现要点

### 9.1 取消与竞态

- 每次新增段落会重新规划，旧任务需 `cancel`
- 转写内部支持 `cancellationCheck`，避免无效计算
- 任务完成时检查 `Task.isCancelled`，避免写入无效结果

### 9.2 音频格式

- 所有段落统一为 16kHz 单声道 PCM
- 拼接时直接按字节顺序拼接

### 9.3 内存与性能

- 段落音频会占用内存，长时间录音需注意
- 准路径在后台执行，不阻塞 UI
- 多批并行可提高整体完成率

## 十、效果与取舍

### 10.1 效果

- **快**：0.8 秒停顿即开始转写，体验接近即时
- **准**：多段拼接后整段转写，长音频准确率更高
- **稳**：准路径未完成时仍用快路径，不增加等待时间

### 10.2 取舍

- 准路径会多算一次转写，有一定算力开销
- 分段越多，规划与任务调度越频繁
- 需在「准确率提升」与「资源消耗」之间做平衡

---

## 十一、总结

通过「快路径 + 准路径」双路径并行，以及「动态规划分批 + 松键时按批合并」的策略，可以在实时语音输入场景下同时兼顾「快」和「准」：

1. **快路径**：停顿即转写，保证反馈及时
2. **准路径**：多段拼接后转写，提升准确率
3. **动态规划**：每批至少 3 段、3 秒，避免过短片段
4. **按批合并**：松键时优先用准路径结果，未完成则用快路径，保证不卡顿

该策略适用于「按住说话」类语音输入产品，在保持实时性的同时，显著提升长段语音的转写质量。
